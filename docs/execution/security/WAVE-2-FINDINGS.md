## WP-14 remediation summary (2026-08-14)
All findings **C1–L2 are FIXED**; every fix carries a named regression test (see the Fix column) that fails before and passes after. Verification: `pnpm -r typecheck`, `pnpm -r lint`, `pnpm -r test` all green (contracts 70, simulator 33, core-api 535, command-web 0 — new AppModule e2e included); `pnpm exec prisma db push` reports "already in sync" and `prisma generate` is clean. The four Wave-2 clean bills were re-run and remain green (append-only, constitution immutability, evaluate-always-ledgers, validatePolicy, identity tenant-filtering).

**Canonical identity layer.** One `Principal` type + `@RequiresAction`/`@Public` decorators + `REQUIRES_ACTION_KEY` now live in `services/core-api/src/common/security/`. The globally-wired `DevAuthGuard`→`AccessGuard` chain builds and reads that one principal; every per-module principal shim and duplicate decorator/guard (events/evidence/ledger/fusion/realtime/presence, and the redundant constitution admin guard) is deleted.

**Platform-singleton policy model (M3).** For Milestone 1 the Constitution is a single platform-wide document (no `organisation_id` column on `constitution_policies`). Altering it therefore requires **platform-level authority**: the activation gate's target is the fixed `PLATFORM_ORGANISATION_ID` constant, so `ORGANISATION_MATCH` passes only for an actor in the platform organisation — a tenant admin is denied. Per-tenant constitutions would require adding an `organisation_id` column and scoping the target to it; the platform singleton is the deliberate Milestone-1 choice (documented in `constitution.service.ts`).

**New dependency:** `@nestjs/throttler` (pre-approved by the directive for M7) — registered in `app.module.ts`, applied to the events ingest and organisation-create routes.
